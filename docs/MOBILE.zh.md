# 移动端技术方案和开发计划

状态：草案，2026-11-10。先做 iPhone，安卓之后再做。

产品定位见移动端设计稿里的“产品属性定义”：手机端只做三件事，拍板、看结果、交代一句。电脑端仍然是干活的地方。

## 1. 已经验证的事

| 验证 | 结果 |
| --- | --- |
| `chat-core` 编到 iOS 模拟器和真机目标 | 通过，代码没有改 |
| `chat-core` 的 87 个测试在 iOS 27.2 模拟器里运行 | 全部通过 |
| 最小应用：SwiftUI + UniFFI + `chat-core`，登录本地沙盒 | 能看群、话题、消息，能发消息 |

还没验证：真机；应用进后台被挂起后再回来的重连和补拉；真机上的钥匙串和应用组（模拟器里已通过）；推送。

## 2. 架构

```
SwiftUI 界面（apps/ios）
        │  生成的 Swift 接口
UniFFI 桥接（crates/chat-ffi）
        │
chat-core（缓存、同步、连接）  ←→  服务器（WebSocket + HTTP）
        │
chat-protocol（协议类型）
```

- **界面**：SwiftUI，用系统控件。面板、通知、实时活动、面容验证都走系统接口。
- **桥接**：`crates/chat-ffi`。只做转换，不放业务逻辑。以后安卓用同一个 crate 生成 Kotlin 接口。
- **核心**：`chat-core` 原样复用。读缓存不等网络，写进发件箱，断线自动重发。
- **服务器**：现有的 Worker 和 Durable Object。新增推送、设备登记和两种登录方式，协议只加不改。

目录：

| 路径 | 内容 |
| --- | --- |
| `crates/chat-ffi` | 桥接 crate 和绑定生成器 |
| `apps/ios/Sources` | 应用的 Swift 代码 |
| `apps/ios/Extensions` | 通知扩展、实时活动扩展 |
| `apps/ios/project.yml` | 工程定义，用 XcodeGen 生成 Xcode 工程（工程文件不进仓库） |
| `apps/ios/Shared` | 应用和扩展共用的类型 |
| `apps/ios/build-sim.sh` | 模拟器构建：编核心、生成接口、生成工程、编应用和扩展；`--run` 装到模拟器并登录本地沙盒 |
| `apps/ios/test-core-sim.sh` | 在模拟器里跑 `chat-core` 的测试 |
| `apps/ios/check-copy.ts` | 界面文字检查 |
| `server/src/push` | 推送模块 |

## 3. 关键决定

1. **界面用 SwiftUI，不用跨平台框架。** 同步引擎已经有一份 Rust 实现，再用别的语言写一份要长期维护两套。
2. **桥接接口是扁平的。** 桥接层暴露少量简单记录（群、话题、消息）和方法，不把协议里的每个类型都搬一遍。
3. **卡片以 JSON 透传。** 卡片结构多、变化快。桥接层把卡片原样作为 JSON 字符串交给 Swift，由 Swift 解码和渲染；不认识的块显示服务器给的文字版本。
4. **变化通知带范围。** 现在的最小应用收到任何变化都整体重读。正式版的通知要说明是哪个群、哪个话题变了，界面只重读那一部分。
5. **私聊直接进聊天。** 每个群和私聊都有一条自己的聊天（协议里 `main` 为真的那个话题）。私聊只有这一个上下文，点进去就是它，不再经过话题列表。群点进去也先到群聊，话题从群聊里进。
6. **凭证进钥匙串，缓存放共享容器。** 钥匙串和缓存目录都放在应用组里，通知扩展才能读到。
7. **工程用 XcodeGen。** 通知扩展、实时活动扩展、签名和上传都需要正式的 Xcode 工程；用一个文本文件定义它，避免工程文件冲突。
8. **产品名只来自 `product.json`。** 构建时写进应用信息，代码和界面文字里不出现。
9. **界面文字有一份目录和一个检查。** 文字集中放在字符串目录里，加一个测试，用和电脑端相同的规则拦住开发用语。
10. **最低系统版本 iOS 17。** 设计稿第三版以后不再依赖玻璃材质；实时活动、按住通知回答都在 17 以内。

## 4. `chat-core` 要改的地方

改动都要保证电脑端行为不变。

- **钥匙串**：`token.rs`、`lib.rs` 和 `Cargo.toml` 里钥匙串相关的条件现在只对 macOS 生效，放宽到 iOS，并支持指定应用组。
- **前后台**：加一个“进后台”的入口，主动收起连接并落盘；回到前台调用已有的 `reconnect_now`。
- **数据目录**：由应用传入共享容器里的路径，核心不用改。
- **客户端名**：连接时报 `mobile`，方便服务器区分设备。

## 5. 服务器要加的

协议变更照仓库规则走：`docs/protocol.md`、`packages/protocol`、`crates/chat-protocol`、`protocol/fixtures` 同一个提交，只加不改。

| 能力 | 做法 |
| --- | --- |
| 设备登记 | 新接口，手机上报推送令牌和平台；新的 D1 表；退出登录时删除 |
| 发推送 | 新模块 `server/src/push`。服务器现在已经为每个成员算出通知原因（提到、等你、有结果、新消息），推送复用这个结果，只在成员需要时发给他登记的设备 |
| 角标 | 推送里带“等你的事”的数量 |
| 通知上回答 | 应用在后台发一次普通的 HTTP 请求回答卡片，不需要长连接 |
| 实时活动 | 运行有进度时，通过实时活动通道更新 |
| 密码登录 | 新接口：设置密码、用邮箱和密码换凭证。密码只存慢哈希 |
| 扫码登录 | 新接口：电脑生成一次性的码，手机扫后确认，电脑拿到新凭证；反过来也支持 |
| 邮箱验证码 | 已有，手机端直接用 |

推送的密钥和证书属于运营方，放在私有的 ops 仓库和 Worker 密钥里，不进这个仓库。

## 6. 里程碑

每个里程碑结束时都能在模拟器里演示，并且测试通过。规模是相对值：小、中、大。

### M0 工程底座（小）

- XcodeGen 工程，应用和两个扩展的空壳。
- 钥匙串和共享容器接好，`chat-core` 的条件编译改完。
- CI 增加一个 macOS 任务：构建桥接和应用，在模拟器里跑 `chat-core` 的测试。
- 界面文字目录和用语检查。
- 完成标准：CI 通过；应用重启后不用重新登录。
- 状态：代码已完成。模拟器里钥匙串、应用组容器、重启后保持登录、退出登录都验证过。真机上的应用组要等有开发者账号签名后再验证。

### M1 能聊（大）

- 邮箱验证码登录。
- 群列表：群和它的话题在一起；私聊直接进聊天。
- 群聊和话题：消息、引用、提到、表情回应、图片和文件、已读位置。
- 发送中、没有发出、离线三种状态。
- 桥接的变化通知改成带范围。
- 顶部的连接状态改成只在不正常时出现。
- 完成标准：和电脑端互发消息，两边一致；断网重连后不丢不重。

### M2 能拍板（大）

- 卡片渲染：先做提问（单选、确认、批准）、结果、字段、链接；其余显示文字版本。
- 首页：等你的事、正在做、今天做完的。
- 批准的二次确认和面容验证。
- 交代。
- 完成标准：电脑端成员发来的提问，在手机上两次点按内答完，卡片原地变成记录。

### M3 通知（大）

- 服务器：设备登记、推送模块、角标。
- 手机：通知权限页、锁屏通知、按住回答、通知中心、通知设置。
- 完成标准：应用没开时，被提到、被等、关注的话题有结果，都能在一分钟内收到通知；不能撤回的操作在通知上只能“打开”。

### M4 账号（中）

- 密码登录、扫码登录、邀请码加入。
- 已登录的设备、面容解锁。
- 完成标准：四种登录方式都能进来；在一台设备上让另一台退出，对方立刻失效。

### M5 其余页面（中）

- 产出列表和查看（网页在隔离的网页视图里）。
- 成员、搜索、单独问。
- 实时查看（只看和停止）和实时活动。

### M6 上真机和发布（中）

- 真机测试：后台挂起、弱网、换网。
- 按产品属性定义里的体验指标验收。
- 内测分发。

## 7. 测试

- **核心**：`chat-core` 的测试在 CI 的模拟器里跑，和在电脑上跑的是同一批。
- **桥接**：`chat-ffi` 加 Rust 测试，覆盖每个导出方法。
- **界面**：关键屏幕做截图对比，浅色和深色各一份。
- **端到端**：对着沙盒服务器，电脑端发、手机端收，和反过来。
- **推送**：推送模块在服务器测试里用假的推送网关验证“发给谁、发什么”。

## 8. 风险和没想清楚的

- **后台挂起**是最大的未知数：手机上长连接随时会断，回前台靠补拉。要在 M1 就上真机试。
- **通知扩展能做多少**：它的内存和时间都很紧，能不能在里面跑 `chat-core` 还不确定。保底做法是推送自带足够显示的内容。
- **卡片覆盖面**：卡片的块和形式很多，手机端第一版只做最常用的几种，其余降级显示。
- **开源协议和应用商店**：仓库是 AGPL，上架应用商店有没有冲突需要专门确认。
- **开发者账号、签名证书、推送密钥**都还没有。
