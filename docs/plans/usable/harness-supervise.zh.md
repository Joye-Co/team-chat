## 0. 总览

| 模块 | 设计了多少 | 实际做了多少 | 最要命的一条 |
| --- | --- | --- | --- |
| 盯活 | 9 种信号、4 种代码处理、9 种模型处理 | 4 种信号、3 种代码处理、0 次叫醒模型 | 电脑失联 2 分钟就取消重来；个人用笔记本合盖即失败 |
| 审批 | 所有运行方式在执行那一步拦 | 只有 Claude Code 拦，且 Unix 上问不到 daemon 就放行 | Codex、ACP、PTY 全靠提示词；默认规则能被常见写法绕过 |

| 评估 | 50 条真实用例进 CI、补丁逐条对比 | 一个手动脚本，标准答案是模型自己当时的答案 | 盯活做了什么，只在 Workers 日志里 |

## 1. 盯活

### 1.1 设计和实现对照

**信号**（设计 9 种）

| 信号 | 做了吗 | 实际规则 | 证据 |
| --- | --- | --- | --- |
| 死了（CLI 进程或电脑） | 一半 | 只看电脑心跳：2 分钟没心跳算失联。不看 CLI 进程在不在 | `server/src/bots/desk/stall.ts:119-128`，`agent/supervise.ts:15` |
| 静了 | 做了 | 5 分钟没事件且没有在跑的步骤，催一次。不分档位 | `stall.ts:98-114`，`supervise.ts:7` |
| 打转 | 四分之一 | 只有「同一个工具标题连续 4 次」。同一报错 3 次、连续无工具结果、连续两轮无成功调用都没做 | `stall.ts:144-156` |
| 没进展（30 分钟无提交无改动） | 没做 | — | — |
| 超时（估时 2 倍） | 没做 | 只有 2 小时硬上限，到点直接取消 | `bots/dispatch.ts:19`，`apps/daemon/src/run.rs:680-684` |
| 等人太久 | 没做 | — | — |
| 只说不做 | 一半 | 结果不超过 200 字、没调用工具、开头像「我来…」就续跑，最多 3 次。「计划里还有没做的步骤」没判 | `supervise.ts:32-38`，`stall.ts:159-177` |
| 额度或供应商出错 | 没做 | CLI 的重试事件被当成「不算进展」，10 分钟后按卡住处理 | `desk/core.ts:181-184`，`events.ts:76-82` |
| 交结果（验收） | 没做 | 完成标准是 CLI 自己报的，没人核对 | `events.ts:509-515` |

**代码直接处理**（设计 4 种）：只说不做续跑 ✅；换备用模型 ❌；CLI 崩了退避重启 ❌（直接记失败，`events.ts:370-373`）；重启后区分「对外动过没有」❌。

**叫醒前台模型后的 9 种处理**：前台模型在盯活里**一次都不会被调用**（`stall.ts` 不引用任何模型；`agent/supervise.ts:1-3` 自述是纯规则）。按规则做到的只有：提醒 ✅、告诉人 ✅、换电脑（实际是从头重来）⚠️。打断重来、换档、拆小、转交、催人、停止都没有。

## 2. 要批准的动作

### 2.1 现状

- 只有 Claude Code 在执行那一步被拦（PreToolUse hook → `chat-run gate` → daemon 匹配正则）。`apps/daemon/src/gates.rs:41-46`：`enforced_by(kind) == "claude"`。
- Codex：`approvalPolicy: "never"` + `sandbox: "danger-full-access"`（`runtime/codex.rs:594-603`），从不请求批准。规则只写在提示词里（`settings/rules.ts:240-245`）。
- ACP、PTY：同样只有提示词。
- Windows 上 Claude Code 低于 2.1.322 也只有提示词（`gates.rs:53-61`）。
- 批准人只有「请求人」和「管理员」两种，可以按动作类型分别设（`rules.ts:203-206`）。

## 3. 多 bot

### 3.1 和 11-09 方向逐条对比

| 11-09 定的方向 | 代码现状 | 结论 |
| --- | --- | --- |
| bot 之间不做文字讨论 | bot 的消息不会触发别的 bot（`bots/room.ts:525-527`） | 一致 |
| 不做 bot 给 bot 派活 | `chat-run handoff`、`assign` 已上线，系统提示词里主动教 CLI 用（`apps/daemon/src/chat_run.rs:92-95`、`1005-1014`；`desk/delegate.ts`；`docs/protocol.md:922-938`） | **冲突，要删或关** |
| 「一个话题一个负责成员」是错的 | 房间里 `bot_topics` 一个话题只存一个 bot；别的 bot 进不来（`room.ts:141-166`、`528-534`；`desk/runs.ts:74`） | **冲突，要改** |
| 靠产出和状态接力 | 没有接力机制；runner bot 读不到产出内容和群里的决定（chat-run 没有 `artifact get`、`decisions`，`chat_run.rs:870-889`） | **缺** |
| 读上下文渐进披露 | 话题消息有（`chat-run topic history/message`）；产出、决定、别人的计划没有 | 缺一半 |
| 可分叉的时间线 | 产出版本没有 `parentVersion`（全仓库搜不到） | **缺** |

## 7. 需要 Joye 决定的（汇总）

1. **bot 派活留不留**（3.3）。11-09 说不做，11-10 对外口径写「能转交、拆分协作」，代码里两种都有。建议：只留「转交」，关掉「分出去」。
2. **接力由谁触发**（3.5）。建议：先只有人 @，加上人在话题里预先写的接力规则；不做服务端自动判断。
3. **接管是什么**（6.1）。建议：这一版就是暂停加留言，词改准；应用内终端排到后面。
4. **电脑失联怎么办**（1.1）。建议：先等，不取消；超过 30 分钟且有别的电脑才换；只有一台电脑时一直等。
5. **单次任务最长多久、到点怎么办**（1.6）。建议：到点自动续，连续两轮没进展才停并告诉人。
6. **盯活要不要调模型**（1.9）。建议：先把规则做对，不调模型；验收（对完成标准）这一项以后再接。
7. **额度用完怎么办**（1.5）、**记忆整理是否必须依赖 API key**（4.6）：和模型层一起定。
8. **成员档位要不要**（2.8）：全开之外，是否提供「先问」「只在工作目录」。建议：不做，保持全开加少数动作审批。
9. **个人使用**：审批默认勾哪几类（2.11）；记忆界面怎么收（4.12）。
10. **分叉时间线**（3.7）：这一版只存父版本关系，还是连界面一起做。建议：只存关系。
