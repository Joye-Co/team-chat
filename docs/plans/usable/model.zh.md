# 模型层审计

范围：服务器上的模型（AI 服务）、执行者的模型、订阅登录和额度、用量和预算、个人使用路径。
依据：本 worktree（main 最新）的代码；#103 的差异单独标出。只读，没有改代码，没有访问生产。
级别：**不可用**＝主流程走不通或结果错；**不完整**＝设计了没做完；**草稿**＝做了，但边界和错误路径没处理，或没经真实使用；**小**＝文案、提示、细节。

## 0. 结论

模型层的主要问题不是"选不了模型"，而是三件事：

1. **出错时没有人知道发生了什么。** 登录失效、额度用完、模型不可用、key 失效，在话题里都是一句"没有完成：" 加 CLI 的英文原文；服务器侧的模型出错则完全静默。没有分类，没有下一步。
2. **调度不看模型层的状态。** 派活时不看 CLI 有没有登录、额度还剩多少、这台电脑有没有选的模型。能读到的信息（登录、额度）只在机器页上显示。
3. **"聪明的那一半"依赖一把单独的 API key，没配时静默关闭。** 前台、摘要、复盘、记忆核对都靠它。界面只说它是"起标题"用的。个人用户大概率只有订阅，没有 API key。

模型的选择入口有三处（成员级已上线、团队级在 #103、常用设置弹窗未提交），加上 daemon.toml 和 CLI 自己的默认，一共五层互相覆盖，实际用了哪个在工作记录里看不到。

## 5. 个人使用路径

## 6. 需要你决定的事

只列会改变产品形态的。

1. **服务器侧的模型要不要必须另配 API key。**
   - A：保持现状，必须配 key。
   - B：没配 key 时，借用电脑上的 CLI 订阅：把前台、摘要、整理的调用交给一台在线电脑上的 CLI 用小模型跑一次。个人用户零配置；代价是依赖一台在线的电脑，延迟更高，还占订阅额度。
   - C：有 key 用 key，没 key 走 B。
   - 我的建议：C。个人使用是一等场景的话，不能要求先去另一家开 API key。

2. **模型设置留几层。** 你 11-09 说过不用这么细。
   - A：只留团队级。前台一个；每种 CLI 一个。成员级从界面去掉（协议字段保留，不再写入）。档位（更快／更强）删掉。
   - B：团队级是默认，成员级留作高级覆盖（#103 现在的做法）。
   - 我的建议：A。常用设置弹窗里不放模型。

3. **成员和 CLI 的关系。**
   - A：运行方式是成员的属性（现状）。
   - B：团队有一个默认运行方式，成员跟着团队；装了多种 CLI 时才能给成员单独选。
   - C：每次任务临时定。
   - 我的建议：B。个人用户通常只有一种 CLI，这一项应该看不见。

4. **订阅额度撞线怎么办。**
   - A：排队等重置，话题里说几点恢复。
   - B：自动换到另一种已登录的 CLI，或另一台电脑。
   - C：只报错并说清原因。
   - 我的建议：默认 A；有第二种已登录的 CLI 或第二台电脑时走 B。派活前先看额度，快到上限就不再派新的。

5. **每周预算对订阅用户算什么。**
   - A：订阅跑的不计入预算，预算只管走 API key 的部分。
   - B：预算改成订阅额度的百分比（例如一个成员最多用掉每周额度的多少）。
   - C：保持现状。
   - 我的建议：先做 A，B 以后再说。
