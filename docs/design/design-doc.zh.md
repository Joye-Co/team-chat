Agent 原生团队协作产品：设计文档
 · 
这是一款桌面端的组织内部工作交流软件：人和 bot 都是一等公民的成员，开发、产品和其他工作都在这里讨论、派活和交付。第一个目标是把它做出来，并且能多人实时使用。本文写产品形态和技术栈，包括服务端和性能。
目标和产品形态
第一个目标是做出一款能多人实时使用的 macOS 桌面交流软件，人和 bot 在里面都是成员。开发、产品和其他工作都在这里进行，员工不再需要飞书和 Slack。
产品里有什么
- 
- 
成员：人和 bot，都有名字、头像、岗位和在线状态。
- 
群和话题：像飞书话题群，群里每条消息都属于一个话题；单聊是两个人的群。
- 
产出：HTML 页面和文件，在独立窗口或侧边面板里看，可以评论、看历史版本。
- 
卡片：bot 发的状态卡、审批卡、表格和图表，原生渲染在时间线里。
- 
你的待办和补课卡片：等你的事放在一处；回来时只看变了什么。
- 
搜索：消息、话题、产出和决定都能搜，中文也要搜得准。
怎样算成功
- 
- 
团队每天的讨论、文档和决定都在这里，不再打开飞书和 Slack。
- 
多人同时在线时，消息实时到达，长话题滚动不卡。
- 
和 bot 协作像和同事协作：在话题里 @ 它，它安静地干活，有结果或需要决定时才出声。
- 
任何一个结果都能追到它的讨论和决定，人和 bot 都能查到“为什么”。
- 
换模型或换 CLI 以后，bot 的身份、记忆和历史都不丢。
不做
- 
- 
手机端，以及 Windows 和 Linux 客户端：先只做 macOS，假设成员都用 Mac。
- 
独立的文档、表格和幻灯片编辑器：先只做 HTML 产出。
- 
各个仓库自己的开发流程（测试、合并）：那是仓库层的事，不在本文。
- 
大公司那种多组织、分片和多级审批。

交流：群、话题和 bot
人和 bot 在同一套群和话题里交流；bot 是群里的成员，不是群外的工具。
- 
- 
群：按团队、项目或主题建；单聊是两个人的群。bot 可以一直待在群里，也可以只在被 @ 时出现。
- 
话题：群里每条消息都属于一个话题。一个话题就是一件事：讨论、派活、进度、产出和决定都挂在它下面，话题有自己的状态。另一件事冒出来，就拆到新话题，两边互相链接。
- 
@ 一个 bot 就是请它接活：它确认一次，然后安静地干活；有结果、需要决定或做不下去时才回到话题。
- 
bot 之间的交接也在话题里：人能看到；同一件事只有一个负责的 bot，避免互相触发、来回刷屏。
- 
长内容放进产出：群里默认一句话；页面、表格和报告放进产出或卡片，话题里只留结论和链接。
- 
提醒默认安静：只有 @ 你、等你决定，或者你关注的话题有了结果，才提醒你。
- 
多人实时：在线状态、“正在输入”、已读位置和未读数实时同步；bot 生成回复时，所有人看到的是同一段流式输出。

客户端只和服务端说话。服务端给每个群一个有序的房间，负责收发和广播，bot 的前台也在服务端；执行者跑在机器上，主动连回服务端。

客户端
客户端是用 Rust GPUI 写的 macOS 应用：界面从本地缓存渲染，网络只负责同步。
- 
- 
组件：GPUI 加 gpui-component（虚拟列表、输入框、Markdown）。不够用的控件自己写。
- 
本地缓存：SQLite（rusqlite）。存成员、群、话题、消息，以及每个群已经收到的顺序号；打开话题时先读本地，再补新的。
- 
长话题不卡：可变高度的虚拟列表，锚在底部；没测量的行先给一个非零的估计高度；bot 的流式增量合并后再刷新；内存里只留最近一段，其余从本地缓存按需读。
- 
输入：中文输入法（候选词、正在拼写的文字）必须正常；支持 @ 成员、引用、粘贴图片和文件。这一项要先做技术验证。
- 
卡片：bot 发的声明式 JSON（A2UI 一类），用自己的组件库原生渲染。
- 
HTML 产出：在独立窗口或侧边面板的 WKWebView 里打开。每个产出一个独立的 origin，严格 CSP，默认断网，从本地缓存加载。gpui-component 的 WebView 还是实验性的，也要先验证。
- 
异步：GPUI 有自己的执行器；网络放在后台线程，结果再交回 UI 线程。
- 
通知：用 macOS 系统通知；应用可以留在菜单栏，保持连接。
- 
登录令牌：存在 macOS 钥匙串里。
- 
发布：签名、公证和自动更新。
服务端：Cloudflare
服务端用 Cloudflare：Workers 做入口，Durable Objects 做群房间、成员连接、bot 前台和机器连接，D1 存全局表和索引，R2 存文件和永久归档，Queues 跑后台任务，Containers 做临时的执行环境。

bot 前台、机器和临时容器
- 
- 
bot 前台：一个 Durable Object。事件进来先排队；一轮模型调用期间到的事件，下一轮一起处理；定时检查用 alarm。它没有执行命令的能力，结构上就“不执行”。
- 
模型调用：前台通过 HTTP 调用模型，等网络的时间不算 CPU；流式输出在前台合并（约 100 毫秒一批）后写进群房间。
- 
派活：前台按标签选机器，把任务交给那台机器的“机器连接”。守护进程确认接单后，任务有租约和心跳；机器断线时，任务等它回来，或按规则换一台。
- 
执行者的事件：守护进程 → 机器连接 → 群房间（话题）和 bot 前台。大的工具输出由守护进程直接上传到 R2，事件里只放引用。
- 
临时容器：新人、新 bot 和临时任务用 Cloudflare Containers。容器由 Durable Object 的代码启动和停止，按运行时间计费；规格从 1/16 vCPU、256 MiB 内存到 4 vCPU、12 GiB 内存。镜像里装好守护进程和需要的 CLI。
- 
主 Mac mini 和成员电脑：只跑守护进程，主动连回“机器连接”；前台和状态都不在这些机器上。
搜索
Durable Object 和 D1 的 SQLite 都支持 FTS5 全文索引；中文的问题在分词，办法是写入时自己切词。
- 
- 
中文切成二字词：写入时把“部署失败”存成“部署 署失 失败”，查询也这样切。这样两个字的词也能搜到，不依赖 trigram 分词。
- 
群内搜索：在群房间自己的 SQLite 里建 FTS5 索引。
- 
全局搜索（跨群，bot 也用）：Queues 把消息送进 D1 的 FTS5 索引。D1 单库最多 10 GB，满了按年份拆库。
- 
语义搜索以后再加，不在第一期。
- 
要实测：二字词索引的效果和占用的空间。
账号和令牌
- 
- 
人：OAuth 或邮件登录。桌面端打开浏览器登录，再通过自定义 URL scheme 回到应用，拿到短期令牌和刷新令牌，存进 macOS 钥匙串。
- 
bot 和机器：各自的长期令牌，D1 里只存哈希；权限跟成员级别走，可以随时吊销。
- 
校验的位置：令牌在 API Worker 或成员连接里校验，权限在进群房间之前检查；群房间只接受内部调用。
环境和部署
- 
- 
两套环境：staging 和 production，各自独立的 Worker、Durable Object 命名空间、D1 和 R2。
- 
位置提示：所有 Durable Object 用同一个位置提示，默认用 oc（大洋洲），让它们在同一地区，互相调用不跨洲。Durable Object 建好后不会搬家，提示只在第一次创建时生效，所以要先定好。
- 
表结构升级：每个 Durable Object 在自己的 SQLite 里记一个版本号，第一次被访问时按版本号升级自己；新代码要能读旧数据。D1 的表用正常的迁移脚本。

风险
- 
- 
热点群：一个群的写入都在一个对象里串行。这个团队规模下没问题；以后真有特别热闹的群，可以按话题拆房间。
- 
位置定了就不好改：Durable Object 不会搬家；位置提示选错了，只能新建对象再迁数据。
- 
绑定 Cloudflare：协议和数据格式是自己定义的，事件日志每天归档到 R2；以后要迁走，可以从归档重建。
- 
服务端 TypeScript、客户端 Rust：两边的类型靠一份协议定义生成（见“协议和同步”）。
协议和同步
客户端、服务端和机器上的守护进程用同一份协议定义：JSON 格式，带版本号，从一个源头生成 Rust 和 TypeScript 的类型。
- 
- 
一份定义，两边生成：协议写成 JSON Schema（或者用 protobuf），生成 Rust 和 TypeScript 的类型，避免两边各写各的。
- 
连接：客户端开一条 WebSocket；断线后自动重连，重连时带上每个群的最后顺序号。
- 
顺序号：每个群的房间给每个事件一个递增的顺序号。客户端按顺序号补齐，不靠时间戳。
- 
事件，不是整份状态：新消息、编辑、撤回、话题状态变化、卡片更新都是事件；客户端把事件应用到本地缓存。
- 
幂等：客户端发消息时带一个自己生成的 ID；网络重试不会产生重复的消息。
- 
流式增量：bot 生成回复时，服务端先把增量合并（比如每 100 毫秒或每 8 KiB 一次）再广播；最后只存完整的消息。
- 
离线和补齐：客户端离线期间的事件，上线后分页拉取；离线太久，就重新同步这个群。
- 
版本：协议带版本号；服务端同时支持当前和上一个版本，客户端太旧时提示更新。

容量估算：消息本身很小，按每天几千条算，一年也只是几百万条，关系库没有压力。占空间的是 bot 的原始 session 和工具输出，所以它们压缩后放进对象存储，数据库里只存索引和摘要。一个群的房间是单线程的，这个规模下每秒的事件远低于它的处理能力。具体数字等接上第一个 bot 后实测。
bot：前台、执行者和机器
每个 bot 成员都分成前台和执行者：前台在服务端常驻，只接待和派活；执行者在机器上干活，主动连回服务端。两者在结构上分开，不靠提示词。
- 
- 
前台不执行：没有 shell 工具，只负责接待、追问、确认、派活，并记住任务之间的关系。它可以用比执行者便宜的模型。DeepSeek 的对照：用中性提示词时 5 次里 0 次委派，p95 29.5 分钟；结构上分开后 p95 15.7 分钟。
- 
执行者一件事一个会话：上下文隔离，用最强的模型。它不直接对人说话，只向前台汇报；要问人时，在汇报里放一个具体问题，前台原样转发。
- 
话题订阅直达：执行者订阅自己的话题和相关的外部对象（文档、工单、PR），之后的回复直接到它，不经过前台。人中途插手，就是在话题里回复。
- 
人优先：前台一轮合并处理多条消息；人的消息优先，并发满了也给人留一个名额。
- 
全双工：长命令 5 秒后转到后台，结果作为新事件回来，执行中也能马上接新消息。
- 
上下文当缓存：消息、话题、session 和决定都有 ID；只注入 ID 和摘要，模型顺着 ID 往回查。
- 
卡住先由代码判断：多久没有新进展（消息、产出、提交），超过阈值才叫 agent 看原因；派两次还没动静，就去看 session 卡在哪，或者把任务拆小。
- 
每件事有授权记录：谁提的、按哪条规则接的、范围多大。

只有一套权限：主体是成员（人或 bot），按级别和范围授权。人能看到、能操作的，同级的 bot 也能。
- 
- 
级别：你这一级（你，以及和你同级的 bot）；成员级（实习生和实习生的 bot）。主 bot 和你同级，实习生的 bot 和实习生同级。
-

-

- 
升级规则：只有业务决定和不可逆的操作才找你；bot 能自己解决的，不叫你。

- 
session 归属：机器记录 CLI 的协议事件流，并原样拷贝 CLI 自己的 session 文件。两者统一成 session → turn → item（消息、工具调用、结果、审批、文件改动），原始文件压缩后放进对象存储。成员自己的电脑只收团队任务里的 session。

换模型不丢东西：历史在产品里。同一个话题中途换模型或 CLI，新的会话从产品的历史里拿交接材料。

- 
双链的来源：产出、提交和外部对象都带上话题 ID，服务端建反向索引；每个对象的页面都显示“哪些地方引用了这里”。
- 
非线性视图：时间线（回来补课时看）；任务图（一个话题派生出的子任务和各自状态）；分支（试两种方案，再合并结论）；“我离开后变了什么”卡片。
分期
这是建议的顺序：先做出能多人实时使用的交流软件，再让 bot 成为成员并接活，最后做产出、卡片和 know-how。每一期满足菱形旁边的条件，才进入下一期。
